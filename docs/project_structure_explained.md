
# Project Structure and Implementation Overview (Detailed)

This document provides a comprehensive explanation of the Playwright + Cucumber test automation project, including folder structure, file purposes, locator strategies, assertions, waits, and best practices. Use this for onboarding, presentations, or deep technical reviews.

---

## Root Directory

- **package.json**: Manages dependencies, scripts, and project metadata. Required for Node.js projects to install and run packages.
- **cucumber.js**: Cucumber configuration (feature file locations, step definitions, output formats).
- **playwright.config.js**: Playwright configuration (browser settings, test directories, timeouts, reporting). Ensures consistent test execution.
- **README.md**: Project documentation, setup, and usage instructions.
- **.gitignore**: Files/folders to exclude from version control (e.g., node_modules, test results).

---

## Folders

- **allure-results/**: Allure test result files for generating detailed test reports.
- **playwright-report/**: Playwright's HTML test reports for visualizing test runs.
- **test-results/**: Stores test output, logs, or artifacts.
- **node_modules/**: Auto-generated by npm, contains all installed dependencies.
- **config/**: (Currently empty) — reserved for custom configuration files (e.g., environment variables, test data).
- **docs/**: Documentation files, e.g., SELECTOR_GUIDELINES.md, to guide best practices for selectors and project usage.
- **features/**: Cucumber feature files (Gherkin syntax). Each file describes test scenarios in plain English, e.g., `scenario1.feature`.
- **pages/**: Page Object Model (POM) files. Each file represents a web page, encapsulating selectors and actions (e.g., `LoginPage.ts`). Promotes code reuse and maintainability.
- **steps/**: Step definition files. Map Gherkin steps from feature files to executable JavaScript/TypeScript code, connecting plain language to automation logic.
- **support/**: Support files like `hooks.ts` (for before/after test hooks) and `fixtures.js` (for shared test data or setup). Manage test lifecycle and context.
- **tests/**: Test specification files, often referencing feature files and step definitions. Each file may target a specific scenario or feature.
- **utils/**: Utility/helper files, e.g., `BasePage.js` (base class for page objects), `constants.js` (shared constants), and `ElementHelper.js` (common DOM actions). Promote DRY (Don't Repeat Yourself) principles.

## Locator Strategies (Selectors)

### Types of Locators Used
- **XPath Selectors**: Used for precise element identification, especially when elements lack unique IDs or classes. Example:
  ```ts
  const menSection = page.locator('//*[@id="categorymenu"]/nav/ul/li[6]');
  ```
- **CSS Selectors**: Used when elements have unique classes or IDs. Example:
  ```ts
  const loginButton = page.locator('#loginFrm_loginname');
  ```
- **Role-based Selectors**: Playwright's `getByRole` for accessibility and robustness. Example:
  ```ts
  const loginButton = page.getByRole('button', { name: 'Login' });
  ```
- **Dynamic/Indexed Selectors**: For lists or repeated elements, index-based XPath is used. Example:
  ```ts
  const productName = (index: number) => `//*[@id="maincontainer"]/div/div/div/div/div[2]/div[${index}]/div[1]/div`;
  ```

### Best Practices
- Prefer role-based or CSS selectors for stability.
- Use XPath for complex or deeply nested elements.
- Use constants for selectors to centralize updates.
- Implement fallback selectors for critical elements.

## Assertions

Assertions are used to validate application state and outcomes. Playwright's `expect` is used for robust, readable checks.

### Examples
- **Visibility Assertion**:
  ```ts
  await expect(loginButton).toBeVisible({ timeout: 10000 });
  ```
- **URL Assertion**:
  ```ts
  await expect(page).toHaveURL(/account\/login/);
  ```
- **Text Assertion**:
  ```ts
  await expect(cartItem).toHaveText('T-shirt');
  ```
- **Count Assertion**:
  ```ts
  await expect(cartItems).toHaveCount(expectedCount);
  ```

### Where Assertions Are Used
- In page objects (e.g., after navigation or actions)
- In step definitions (to validate scenario outcomes)
- After critical user actions (e.g., login, add to cart)

### Best Practices
- Assert after every navigation or major action.
- Use descriptive error messages for custom assertions.
- Prefer Playwright's built-in expect for reliability.

## Waits and Synchronization

Proper waits are crucial for reliable automation. This project uses a mix of Playwright's auto-waiting, explicit waits, and custom timeouts.

### Types of Waits Used
- **Auto-waiting**: Playwright automatically waits for elements to be actionable.
- **Explicit Waits**:
  - `waitForSelector` or `locator.waitFor({ state: 'visible' })` for element visibility.
  - `waitForLoadState('networkidle')` for page/network stability.
  - `waitForTimeout(ms)` for fixed delays (used sparingly, e.g., for animation completion).

### Examples
```ts
await page.waitForLoadState('networkidle', { timeout: 15000 });
await expect(element).toBeVisible({ timeout: 10000 });
await page.waitForTimeout(1000); // For smooth scrolling or animation
```

### Where Waits Are Implemented
- After navigation (to ensure page is loaded)
- Before/after clicking elements (to ensure visibility and stability)
- After actions that trigger UI changes (e.g., sorting, adding to cart)

### Best Practices
- Prefer Playwright's auto-waiting and expect over fixed timeouts.
- Use explicit waits for dynamic or slow-loading elements.
- Avoid excessive use of `waitForTimeout` unless necessary for UI animation.

## Example: Key File Explanations

### playwright.config.js
Configures Playwright's test runner, browser options, timeouts, and reporting. Ensures consistent test execution across environments.

### features/scenario1.feature
Describes a user scenario in Gherkin. Example:
```gherkin
Feature: Shopping Cart
  Scenario: Add item to cart
    Given I am on the home page
    When I add an item to the cart
    Then the cart should show 1 item
```
This makes tests readable for non-developers.

### pages/LoginPage.ts
Implements the Page Object Model for the login page. Encapsulates selectors and login actions, e.g.:
```ts
class LoginPage {
  async login(username: string, password: string) {
    const usernameField = this.page.locator('#loginFrm_loginname');
    const passwordField = this.page.locator('#loginFrm_password');
    const loginButton = this.page.getByRole('button', { name: 'Login' });

    await expect(usernameField).toBeVisible({ timeout: 10000 });
    await expect(passwordField).toBeVisible({ timeout: 10000 });
    await expect(loginButton).toBeVisible({ timeout: 10000 });

    await usernameField.fill(username);
    await passwordField.fill(password);
    await loginButton.click();

    // Assertion after login
    await expect(this.page.locator('//a[contains(text(),"Welcome back")]')).toBeVisible({ timeout: 1000 });
  }
}
```
This abstraction makes tests more maintainable and robust.

### steps/scenario1.steps.ts
Maps Gherkin steps to Playwright actions, e.g.:
```ts
import { When, Then } from '@cucumber/cucumber';

When('I navigate to the home page', async function() {
  const homePage = (this as any).homePage;
  await homePage.clickHomeNav();
});

When('I add the newest product to the cart', async function() {
  const productPage = (this as any).productPage;
  await productPage.addNewestItemToCart();
});

Then('I should see {int} item in the cart', async function(count: number) {
  const cartPage = (this as any).cartPage;
  await cartPage.assertItemInCart(count);
});
```

### pages/HomePage.ts
Implements navigation and smooth scrolling. Example:
```ts
async clickDoveBrandFromCarousel() {
  const brandCarousel = this.page.locator('//*[@id="brandcarousal"]');
  await expect(brandCarousel).toBeVisible({ timeout: 15000 });
  await this.smoothScrollToElement('#brandcarousal', 1200);
  const doveBrand = this.page.locator('//*[@id="brandcarousal"]/li[7]');
  await expect(doveBrand).toBeVisible({ timeout: 20000 });
  await doveBrand.click();
}

private async smoothScrollToElement(selector: string, duration: number = 1000) {
  await this.page.evaluate(({ selector, duration }) => {
    const element = document.querySelector(selector);
    if (element) {
      element.scrollIntoView({ behavior: 'smooth', block: 'center', inline: 'nearest' });
    }
  }, { selector, duration });
  await this.page.waitForTimeout(duration + 200);
}
```

### pages/ProductPage.ts
Implements sorting and waiting for UI updates. Example:
```ts
async sortByHighToLow() {
  const sortDropdown = this.page.locator('//*[@id="sort"]');
  if (await sortDropdown.isVisible()) {
    await sortDropdown.click();
    await this.page.waitForTimeout(500);
    await sortDropdown.selectOption({ index: 4 });
    await this.page.waitForLoadState('networkidle', { timeout: 12000 });
    await this.page.waitForTimeout(3000);
  }
}
```

### pages/CartPage.ts
Implements cart navigation and assertions. Example:
```ts
async goToCart() {
  const cartElement = this.page.locator('//div[@id="cart_checkout1"]');
  if (await cartElement.isVisible()) {
    await cartElement.click();
  }
  await this.page.waitForLoadState('networkidle', { timeout: 15000 });
  await this.page.locator('//h1[contains(text(),"Shopping Cart")]').waitFor({ state: 'visible', timeout: 5000 });
}
```

## Why This Structure?
- **Separation of concerns**: Keeps feature files, step definitions, page objects, and utilities organized and maintainable.
- **Reusability**: Page objects and utilities can be reused across tests.
- **Readability**: Gherkin feature files are easy for all stakeholders to understand.
- **Scalability**: New features, pages, and tests can be added with minimal changes to existing code.
- **Maintainability**: Changes in UI or logic are isolated to specific files, reducing the risk of breaking multiple tests.
